# Project Harmony - UI 颜色系统审计报告

**角色:** UI 重构工程师 (Agent)  
**日期:** 2026年3月1日  
**状态:** 已完成审计  

## 1. 执行摘要

基于对 Project Harmony 中 68 个 UI 相关脚本文件的全面扫描与审计，我们发现了严重的颜色硬编码问题。尽管项目已建立了 `ui_colors.gd` 作为全局颜色规范的单一事实来源，但在实际开发中，大量脚本未使用该单例，导致了视觉风格碎片化、维护成本增加以及未来主题切换功能的实装障碍。

**核心发现：**
- **扫描文件总数:** 68 个 `.gd` 脚本
- **未使用 UIColors 的文件:** 11 个（占比约 16%）
- **硬编码颜色总数:** 116 处
- **独特的硬编码颜色值:** 94 种

## 2. 颜色使用规范冲突分析

通过对比《美术与VFX方向总文档》(Art_And_VFX_Direction.md) 和 `ui_colors.gd`，我们发现了以下规范冲突和缺失：

### 2.1. 音符颜色定义冲突
在设计文档《UI_Design_Module3_IntegratedComposer.md》中，音符颜色被明确定义，但在代码实现中出现了偏差：

| 音符 | 文档定义 | ui_colors.gd 现状 | 冲突说明 |
|:---:|:---|:---|:---|
| C | 谐振青 `#00FFD4` | 红 `#FF6B6B` | 完全不一致，破坏了"中性冷色"的设计意图 |
| D | 疾风蓝 `#0088FF` | 橙 `#FF8C42` | 完全不一致 |
| E | 翠叶绿 `#66FF66` | 黄 `#FFD700` | 完全不一致 |
| F | 深渊紫 `#8844FF` | 绿 `#4DFF80` | 完全不一致 |
| G | 烈焰红 `#FF4444` | 青 `#4DFFF3` | 完全不一致 |
| A | 烈日橙 `#FF8800` | 蓝 `#4D8BFF` | 完全不一致 |
| B | 霓虹粉 `#FF44AA` | 紫 `#9D6FFF` | 完全不一致 |

**结论:** `ui_colors.gd` 中的 `NOTE_COLORS` 字典完全采用了另一套彩虹色系，必须重构以对齐设计文档。

### 2.2. 全局基础色偏差
- **主背景色:** 文档定义为深渊黑 `#0A0814`，`ui_colors.gd` 一致。但在 `main_menu.gd` 中硬编码了 `#0A0814` 和带有透明度的 `Color(0.078, 0.063, 0.149, 0.8)`。
- **面板背景色:** 文档定义为星空紫 `#141026`，`ui_colors.gd` 一致。但在 `game_over.gd` 中硬编码了该值。

## 3. 硬编码颜色重灾区

以下是硬编码颜色问题最严重的文件列表（按问题数量排序）：

### 3.1. `ui_theme_manager.gd` (32处)
该文件本应是主题管理的核心，却在 `CHAPTER_UI_COLORS` 字典中硬编码了大量颜色，如 `Color(1.0, 0.95, 0.7)`、`Color(0.6, 0.3, 0.8)` 等。这些章节颜色应当在 `ui_colors.gd` 中统一管理。

### 3.2. `main_game.gd` (25处)
存在大量用于敌人、特效和章节颜色的硬编码。
- 敌人颜色：`Color(0.7, 0.3, 0.3)` (红), `Color(0.2, 0.1, 0.4)` (深紫) 等。
- 章节颜色：`Color(0.0, 1.0, 0.83)` (Ch0), `Color(0.6, 0.3, 0.8)` (Ch1) 等。
- 屏幕闪烁：`Color(1.0, 0.9, 0.3, 0.6)`。

### 3.3. `test_chamber.gd` (22处)
作为测试场景，使用了大量的本地常量和硬编码，如 `GRID_COLOR = Color(0.08, 0.06, 0.14, 0.5)`。虽然是测试场景，但也应尽可能使用全局颜色以保证测试效果的准确性。

### 3.4. `player_visual_enhancer.gd` (16处) & `spell_visual_manager.gd` (7处)
这两个文件在 `TIMBRE_COLORS` 字典中硬编码了音色对应的颜色：
- `0: Color(0.0, 1.0, 0.83)` (谐振青)
- `1: Color(0.8, 0.6, 0.2)` (温暖金色)
- `2: Color(0.4, 0.7, 1.0)` (天蓝色)
这些颜色实际上在 `ui_colors.gd` 中已经有部分定义（如 `TIMBRE_SYNTH`），应当统一引用。

### 3.5. `game_over.gd` (15处)
在文件顶部定义了大量本地常量：
```gdscript
const PANEL_BG := Color("#141026")
const ACCENT_COLOR := Color("#9D6FFF")
const TEXT_PRIMARY := Color("#EAE6FF")
```
这些完全重复了 `ui_colors.gd` 中的定义，是典型的"未引用全局单例"案例。

### 3.6. `boss_guido.gd` (12处)
Boss脚本中硬编码了特定的Boss颜色，如 `Color(0.9, 0.75, 0.2)`。`ui_colors.gd` 中已有 `BOSS_PHASE_COLORS`，应当将这些Boss专属颜色迁移到全局配置中。

## 4. 颜色值复用情况

扫描发现部分硬编码颜色被多次重复使用，这进一步证明了将其提取为全局常量的必要性：

1. **谐振青变体 `Color(0.0, 1.0, 0.83)`**: 出现 10 次（在 `main_game.gd` 和视觉增强脚本中）。
2. **危险红 `Color(1.0, 0.3, 0.3)`**: 出现 4 次。
3. **故障洋红变体 `Color(1.0, 0.0, 0.5)`**: 出现 4 次（在Boss和敌人视觉脚本中）。
4. **主强调色 `#9D6FFF`**: 出现 3 次（被作为本地常量重复定义）。
5. **章节/音色蓝色 `Color(0.0, 0.5, 1.0)`**: 出现 3 次。

## 5. 结论

项目中的颜色硬编码问题主要分为三类：
1. **重复定义:** 开发者知道规范颜色，但选择在本地重新定义 `const COLOR = Color("#...")` 而不是引用 `UIColors.COLOR`。
2. **逻辑内联:** 在特效、渲染、缓动动画中直接写入 `Color(r, g, b)`。
3. **规范缺失/冲突:** 部分系统（如章节颜色、音色颜色）在全局规范中定义不全，导致开发者只能自行硬编码；或者全局规范与设计文档冲突（如音符颜色）。

解决这些问题将是下一步迁移计划的核心目标。
